# Этапы 12–14: API, протокол и интерфейс

## Запуск

Из корня репозитория, после установки зависимостей и подготовки локальных моделей
по README и [PIPELINE.md](PIPELINE.md):

```powershell
.venv/Scripts/python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

Откройте **http://127.0.0.1:8000/**. Отдельный frontend-сервер, Node, Streamlit,
CDN или платный API не нужны. HTML/CSS/JS находятся в `frontend/` и отдаются FastAPI.
Для DOCX/PDF установите `requirements-export.txt` (уже включён в requirements-dev).
Для реальной обработки нужны ffmpeg, faster-whisper с локальными весами,
Community-1 с локальными весами и настроенная локальная Ollama.
Страница запускается без моделей; при попытке обработки API сообщает об их отсутствии.

1. Введите название, при наличии — дату встречи. Выберите WAV/MP3/M4A/MP4/WebM.
2. Нажмите «Загрузить файл»; backend сохранит запись и подготовит WAV.
3. Нажмите «Обработать». UI показывает текущую стадию из `/pipeline/status`.
4. Откройте вкладки «Саммари», «Поручения», «Транскрипт».
5. Ссылки «Фрагмент …» переводят к исходной реплике; поручения содержат цитаты.
6. Скачайте DOCX/PDF. Встречу можно открыть повторно по URL с `#meeting_id`.

Переключение вкладок работает с уже загруженным объектом. Перезагрузка страницы,
«Обновить результат» и скачивание используют только GET. POST анализа выполняется
только по нажатию «Обработать». Готовый анализ повторно не запускается и на сервере.
При ошибке загрузки можно выбрать другой файл для той же созданной встречи.
При штатной ошибке pipeline повтор разрешён и использует готовые стадии.

Обработка пока синхронная в backend, без очереди: браузер держит POST открытым,
параллельно читая статус примерно раз в 1,2 секунды. Процент готовности и оставшееся
время не выдумываются. После разрыва связи сначала обновите состояние. Перезагрузка
страницы не отменяет начатую обработку; аварийное завершение сервера по-прежнему
может оставить статус `running` и требует ручного восстановления.

## API

| Endpoint | Поведение |
| --- | --- |
| `POST /meetings` | `title` и необязательный `meeting_date` в формате `YYYY-MM-DD`; 201 |
| `POST /meetings/{id}/analyze` | Существующий pipeline после upload, включая экспорт; 200 со статусом и ссылками |
| `GET /meetings/{id}/result` | Только сохранённый результат; 200, либо 409 `analysis_not_ready` |
| `GET /meetings/{id}/pipeline/status` | Текущая стадия, состояние, код ошибки и ссылки экспорта |
| `GET /meetings/{id}/exports/docx` | Сохранённый DOCX |
| `GET /meetings/{id}/exports/pdf` | Сохранённый PDF |

`/process` сохранён как совместимый маршрут того же обработчика, `/analysis` —
как подробный GET со счётчиками LLM. Неизвестный ID возвращает 404, неверный UUID — 422.
Конкурентный запуск блокируется существующим claim в SQLite.

`/result` возвращает ровно четыре верхних поля:

```json
{
  "meeting": {"id": "…", "title": "…", "status": "transcribed", "created_at": "…", "meeting_date": null},
  "summary": {"topics": [], "key_discussions": [], "decisions": [], "problems_and_risks": [], "main_action_items": []},
  "action_items": [],
  "transcript": []
}
```

В `transcript` находятся сохранённые aligned segments: `id`, `text`, `start`, `end`,
`speaker`, `speaker_ids`, `ambiguous`. Итог доступен даже после ошибки экспорта,
поскольку анализ сохраняется раньше. GET не создаёт файлы, не запускает STT,
диаризацию, alignment или LLM и не меняет базу.

Дата встречи вводится пользователем и хранится в дополнительной таблице
`meeting_details`, создаваемой при старте. Существующая таблица `meetings` и её
данные не изменяются. Без подтверждённой даты возвращается `null`; время создания
записи не подставляется вместо даты встречи. Относительные сроки сохраняются как есть.

## Документ

Оба формата используют одну структуру обычного Python-шаблона:

- ПРОТОКОЛ СОВЕЩАНИЯ — название и дата;
- КРАТКОЕ САММАРИ — темы, обсуждения, риски и основные поручения;
- КЛЮЧЕВЫЕ РЕШЕНИЯ — с условиями, если они есть;
- ПОРУЧЕНИЯ — таблица «№ / Поручение / Ответственный / Срок»;
- ТРАНСКРИПТ — исходный текст с ID, временными метками и метками говорящих.

Сохраняются условия, промежуточные сроки, ссылки на сегменты и цитаты. Неизвестные
значения явно отмечены. Длинная таблица переносится по страницам; её шапка повторяется.
Сначала создаётся DOCX через python-docx, затем PDF через ReportLab с локальным TTF
и проверкой RU/KZ глифов. LLM при экспорте не используется. Скачивание открывается
после успешного создания обоих файлов. При сбое повтор pipeline использует анализ
из базы. Существующие готовые протоколы автоматически не переформатируются.

Основа: [python-docx](https://python-docx.readthedocs.io/en/latest/user/quickstart.html),
[таблицы ReportLab](https://docs.reportlab.com/reportlab/userguide/ch7_tables/),
[локальные static files FastAPI](https://fastapi.tiangolo.com/tutorial/static-files/).


Браузерные тесты поднимают отдельный localhost-сервер и временную SQLite. Они
проверяют загрузку/повтор после повреждённого файла, progress, вкладки, цитаты,
скачивание, перезагрузку, отсутствие внешних HTTP-запросов и дополнительных AI-вызовов.
Ширины экранов — 1280 и 390 px. QA-файлы находятся в игнорируемой `data/qa/stage14`.
Используются явные STT/diarization/LLM doubles; это не проверка качества моделей.
API-тесты также проверяют отсутствие inference при чтении после перезапуска,
таблицы/заголовки/даты/пустые данные и длинную строку PDF на нескольких страницах.
PDF и UI просмотрены визуально; DOCX проверен структурно через python-docx.
Визуальная вёрстка DOCX в Word/LibreOffice отдельно не подтверждена.

## Границы MVP

Сохранены локальный режим и отсутствие авторизации: сервер предназначен для
запуска на `127.0.0.1`. UI выводит текст через `textContent`, без выполнения HTML
из модели/транскрипта, а страница ограничивает подключения своим origin через CSP.
Редактирование протокола и сопоставление имён в UI в этот этап не входят;
существующий `/speakers` доступен через API до анализа.
В текущей среде реальные Community-1 и Ollama ещё не готовы, поэтому качество
полного ML-сценария на RU/KZ аудио не подтверждено.
