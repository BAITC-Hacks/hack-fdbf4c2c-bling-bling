# Этапы 10–11: один анализатор и экономный pipeline

Обновление этапов 12–14: появился совместимый `POST /analyze`, объединённый
`GET /result`, шаблоны протокола и локальный UI. `/process` продолжает работать.
Подробности: [UI.md](UI.md).

Основной сценарий теперь:

`POST /upload → POST /process → transcription → diarization → alignment → LocalMeetingAnalyzer → validation → SQLite → DOCX/PDF`.

Загрузка/ffmpeg, STT, диаризация и прежние GET endpoints сохранены. Их рабочий код
не переписан. Prompts этапов 8–9 остаются отдельными UTF-8 файлами. Новый pipeline
не вызывает `extract()` и `summarize()` последовательно: поручения и summary
получаются одним совместным JSON-ответом. Старые отдельные POST остаются для
совместимости и отладки; для основного сценария используйте `/process`.

## Количество вызовов

| Случай | Inference |
| --- | --- |
| Непустая запись помещается в контекст вместе с инструкцией | 1: action_items + summary |
| Пустой транскрипт | 0 |
| Готовый pipeline вызван повторно, в том числе после перезапуска | 0 новых |
| Ошибка экспорта после успешного анализа | При повторе 0 новых; используется сохранённый анализ |
| Есть совместимые готовые поручения и summary старой версии | 0 новых; режим reused |
| Полный вход не помещается в контекст | Компактные facts/action_items каждой части + 1 финальный merge |

Ollama `/api/show` проверяет локальность модели, не выполняет генерацию и не
получает текст встречи. `generation_requests` считает попытки отправки запроса
генерации, включая отклонённые по контексту; `completed_generations` — завершённые
ответы модели. Эти счётчики не включают metadata-запросы и не являются оценкой
качества модели. `chunks` показывает число успешно разобранных частей.

## Chunking только после подтверждённого переполнения

`LocalMeetingAnalyzer` сначала отправляет весь транскрипт с одной схемой
`AnalysisDraft`: список поручений и `SummaryDraft`. Новое подключение Ollama
использует `server_context_check=True`: консервативная старая оценка по UTF-8 байтам
не включает chunking заранее. `truncate=false` и `shift=false` запрещают молча
терять начало текста. Нужна версия локального сервера, поддерживающая эти поля.
Контракт сверялся с [исходниками Ollama](https://github.com/ollama/ollama/blob/main/api/types.go).

Только явный ответ сервера о превышении входного контекста запускает деление.
Таймаут, отсутствие модели, невалидный JSON или недостоверные цитаты не запускают
дополнительные генерации. Автоматического retry невалидного ответа в новом
анализаторе нет — он завершается понятной ошибкой.

Большая запись делится на две части с балансировкой по объёму текста, преимущественно
по границам сегментов. Если часть также не помещается, деление повторяется в пределах
лимитов. Длинный одиночный сегмент может делиться по словам, сохраняя исходный ID;
текст не обрезается. Фрагменты проверяются отдельно, итоговые цитаты — по полному
исходному сегменту.

Каждая часть возвращает **только факты и кандидаты поручений**, без summary.
Особо сохраняются короткие ответы, условия и исправления сроков, даже если без
предыдущей части они ещё не дают самостоятельного поручения. Глобальные ID и
порядок частей сохраняются. После всех частей выполняется ровно один совместный
merge. Он должен сопоставить поздние исправления с ранними назначениями, объединить
повторы и сформировать итоговое summary.

Если финальные факты не помещаются в контекст, возвращается ошибка — рекурсивных
summary/merge нет. Если модель не сохранила важный факт в частях, валидаторы не
восстановят его автоматически. Качество межчастного согласования требует реальной
LLM-оценки; unit tests с doubles проверяют только контракт и бюджет.

| ENV | Default | Назначение |
| --- | --- | --- |
| `HACKALEM_ANALYSIS_MAX_REQUESTS` | 12 | Жёсткий лимит всех generation requests одного запуска, включая отклонённые |
| `HACKALEM_ANALYSIS_MAX_CHUNKS` | 6 | Максимум успешно разобранных частей |
| `HACKALEM_LLM_NUM_CTX` | 32768 | Общая настройка запрошенного контекста, ограничивается моделью |
| `HACKALEM_LLM_NUM_PREDICT` | 4096 | Лимит токенов ответа, в том числе совместного JSON |

Лимиты старых `EXTRACTION_MAX_CHARS`/`SUMMARY_MAX_CHARS` и их retries относятся
к старым отдельным сервисам. Новый анализатор ориентируется на ответ сервера и
лимиты числа запросов, не режет запись по фиксированному числу символов.
Если совместный ответ обрезан по `num_predict`, он не сохраняется. Это не повод
делить вход автоматически — настройте размер ответа/контекста для своей модели.

## Alignment

В репозитории до этого изменения alignment отсутствовал. Добавлен небольшой
`AlignmentService`, не меняющий текст, ID и временные метки STT. Он сопоставляет
интервалы сегментов с результатом диаризации. Имя применяется только к одному
говорящему при покрытии не менее половины сегмента и наличии ручного сопоставления.
Этот порог — настройка реализации, не требование ТЗ.

Если в сегменте несколько голосов, смена говорящего, мало покрытия или нет речи
диаризации, сохраняются метки и `ambiguous=true`; имя остаётся неизвестным.
Не выполняются биометрическая идентификация, деление реплик по словам или
выдуманное назначение говорящего. Снимок alignment сохраняется в SQLite и используется
в экспорте. При необходимости назначьте имена через существующий `/speakers` после
диаризации, но до запуска анализа; готовый протокол — снимок данных на момент анализа.

## Запуск и API

Подготовьте ранее описанные STT, Community-1 и локальную LLM. Ollama запускайте
с `OLLAMA_NO_CLOUD=1`; локальные веса скачиваются заранее. Автоматического cloud
fallback, `pull` моделей при inference и платных AI API в pipeline нет.

Для локального экспорта:

```powershell
.venv/Scripts/python.exe -m pip install -r requirements-export.txt
```

PDF использует локальный TTF: Arial в Windows или DejaVu Sans в стандартном пути
Linux. Другой файл задаётся через `HACKALEM_PDF_FONT_PATH`. Перед созданием PDF
проверяется наличие всех используемых глифов, включая казахские. При отсутствии
шрифта возвращается ошибка; скачивания шрифта нет.

После создания встречи и загрузки записи:

```powershell
Invoke-RestMethod "http://127.0.0.1:8000/meetings/$($meeting.id)/process" -Method Post
Invoke-RestMethod "http://127.0.0.1:8000/meetings/$($meeting.id)/pipeline/status"
Invoke-RestMethod "http://127.0.0.1:8000/meetings/$($meeting.id)/analysis"
Invoke-WebRequest "http://127.0.0.1:8000/meetings/$($meeting.id)/exports/docx" -OutFile protocol.docx
Invoke-WebRequest "http://127.0.0.1:8000/meetings/$($meeting.id)/exports/pdf" -OutFile protocol.pdf
```

Результат `/process` содержит состояние, текущую стадию, код ошибки и ссылки
экспорта. Существующие GET `/action-items` и `/summary` читают представления единого
анализа, без дополнительных LLM-вызовов. Версия инструкции в них — `joint-1`.

Экспорт содержит summary, все поручения со сроками/milestones/условиями, ссылки и
цитаты поручений, полный транскрипт с временными метками и говорящими. DOCX/PDF
строятся локально, без LLM. Файлы находятся в
`data/exports/{meeting_id}/protocol.docx` и `protocol.pdf`. Временные файлы удаляются
при ошибке, скачивание доступно только после готовности обоих форматов.

## Сохранение и повтор

Добавлены таблицы `meeting_pipelines` и `meeting_analyses`. Состояние pipeline
отдельное от STT. Claim в SQLite блокирует конкурентный запуск, а резервирование
представлений поручений/summary — параллельный запуск старых POST.
Готовые транскрипт и диаризация переиспользуются. После валидации единый анализ,
alignment и совместимые представления записываются транзакцией **до экспорта**.
Поэтому ошибка шрифта/диска/экспорта не приводит к повторной работе LLM.

Если обе старые стадии уже готовы и относятся к одинаковым источникам, pipeline
проверяет их совместимость и использует их без новой генерации. Если готово только
извлечение, новый совместный анализ формирует оба результата; при его ошибке старый
результат восстанавливается. При изменении исходного транскрипта, alignment,
настроенного имени модели или prompt после сохранения нового анализа повтор
незавершённого pipeline отклоняется, чтобы не смешивать версии. Для нового анализа
используйте новую встречу. Готовый `/process` идемпотентно возвращает прежний результат.

Штатная ошибка оставляет `status=failed`, стадию и безопасный `error_code`.
Повтор возобновляется с готовых стадий. Аварийное завершение процесса может оставить
`running`; автоматического восстановления таких операций пока нет. Промежуточные
факты chunks при неуспешном финальном merge не кешируются между запусками.

## Проверки и ограничения

**170 тестов прошли**, HTTP `/health` — 200, compileall без ошибок. Старые
155 тестов сохранены. Новые проверяют один joint request, chunks → facts → один
merge, перенос исправленного срока между частями, бюджет, одиночную длинную реплику,
отказ от рекурсивных summary, alignment, конкурентность, совместимость и повторы.

В сквозном тесте настоящие загрузка/ffmpeg, SQLite, DOCX/PDF. Оба файла открыты
библиотеками, извлечённый текст содержит русский, проценты, сроки и казахские глифы.
STT, диаризация и LLM в этом тесте — явные doubles. Полный inference с настоящими
моделями не проверен: Community-1 ожидает веса, Ollama/модель не подготовлены.
Это не заявление о готовности ML-качества MVP. Визуальная приёмка длинных протоколов,
многоголосой RU/KZ записи и смысловой корректности анализа остаётся отдельной проверкой.
