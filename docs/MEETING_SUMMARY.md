# Этапы 8–9: prompts и summary

Источник: F-08, F-09 и ограничения §4 в
[ai-review/requirements.md](../ai-review/requirements.md), а также текущий запрос.

## Отдельные инструкции модели

- `app/prompts/action_items.txt` — инструкция извлечения поручений со всеми правилами этапа 7 и прямым запретом выдумывать людей, факты, поручения и сроки.
- `app/prompts/meeting_summary.txt` — инструкция формирования пяти разделов summary.
- `app/prompts/__init__.py` читает UTF-8 относительно папки модуля, независимо от текущей рабочей директории. Пустой, отсутствующий или поврежденный файл дает `503 prompt_unavailable`.

Огромных строк prompt в Python больше нет. JSON Schema добавляется программно,
короткая инструкция повтора остается в коде. Файлы перечитываются при запросе.
Новые результаты извлечения имеют `prompt_version="2"`, чтение старых с версией
`"1"` сохранено. У summary версия инструкции — `"1"`.

## Сервис и данные

`MeetingSummaryService.summarize(segments, action_items)` использует тот же
`LocalLLMClient.generate_json`, что и извлечение. Бизнес-логика не импортирует
Ollama; адаптер подключается в `app/main.py`. Действуют существующие ограничения
loopback, preflight локальных весов, запрет proxy/redirects и облачного fallback.
Подготовка Ollama и отключение облака описаны в [ACTION_EXTRACTION.md](ACTION_EXTRACTION.md).

Сервис возвращает пять разделов:

| Поле | Содержание |
| --- | --- |
| `topics` | Темы совещания |
| `key_discussions` | Ключевые обсуждения; предложения/предположения должны быть явно обозначены в тексте |
| `decisions` | Принятые решения; у условных сохраняется условие |
| `problems_and_risks` | Озвученные проблемы и риски |
| `main_action_items` | Выбранные основные поручения, скопированные из результата этапа 7 |

Каждый пункт первых четырех разделов содержит `text`, `source_segment_ids` и
`evidence` — список `{segment_id, quote}`. У решения дополнительно есть
`decision_type: accepted | conditional` и `condition: string | null`.
Условное решение без условия и обычное решение с условием схема отклоняет.
Пустой раздел представлен `[]`, неизвестное условие обычного решения — `null`.

LLM возвращает только индексы основных поручений из входного списка. Код проверяет
их существование/уникальность и копирует выбранные записи целиком, включая
ответственного, `deadline_raw`, milestones, условия и источники. При непустом
списке нужно выбрать хотя бы одно поручение. Это предотвращает изменение задач
при повторном пересказе, но не исправляет возможные ошибки предыдущего извлечения.

## API

Сначала нужны готовый транскрипт и результат извлечения поручений, даже если
поручений не найдено. Вызовы из PowerShell после настройки модели:

```powershell
Invoke-RestMethod "http://127.0.0.1:8000/meetings/$($meeting.id)/extract-action-items" -Method Post
Invoke-RestMethod "http://127.0.0.1:8000/meetings/$($meeting.id)/summarize" -Method Post
Invoke-RestMethod "http://127.0.0.1:8000/meetings/$($meeting.id)/summary"
Invoke-RestMethod "http://127.0.0.1:8000/meetings/$($meeting.id)/summary/status"
```

Если извлечение уже завершено, первый POST повторять не нужно.
POST `/summarize` синхронный, без тела. Повтор завершенного/выполняющегося запроса
дает 409; GET читает SQLite, не вызывает LLM. Статус отдельный:
`not_started → running → ready`. Статус STT и доступ к поручениям не меняются.
После обычной ошибки claim удаляется, запрос можно повторить. Аварийное завершение
процесса может оставить `running`; восстановления таких операций пока нет.

В таблицу `meeting_summaries` одной транзакцией сохраняются summary, снимок исходных
сегментов, модель, версия prompt и SHA-256 исходного транскрипта/списка поручений.
Hash вычисляется от UTF-8 результата `model_dump_json()`. Снимок источников возвращается
в `source_segments`. Существующие таблицы не пересоздаются. Отдельного `summary.json`
нет, JSON доступен через GET.

Если транскрипт изменен после извлечения, формирование блокируется с
`409 summary_source_mismatch`. Нельзя незаметно объединить задачи и текст из
разных версий встречи. Alignment этапа 6 пока отсутствует; неподтвержденные имена
говорящих не добавляются.

## Проверки и их границы

- Строгая Pydantic/JSON Schema отклоняет лишние поля и неверные типы; Markdown, повторные JSON-ключи и NaN не принимаются.
- Все ссылки должны существовать; цитаты должны совпадать с исходными репликами с допустимой нормализацией регистра/пробелов/Unicode.
- Каждое число в тексте пункта должно присутствовать в его подтверждающих цитатах. Нельзя подставить число из другой, не процитированной реплики. Проверяются цифровые записи, включая дроби и проценты: `94%` и `94` различаются.
- Условие решения должно присутствовать в цитатах. Инструкция запрещает менять отрицания, факты, единицы измерения и статус предложений или добавлять отсутствующие сроки.
- Невалидный ответ повторно запрашивается ограниченное число раз, затем возвращается ошибка без сохранения.

Проверка чисел — лексическая, не семантическая. Она не доказывает правильность
связи числа с показателем и не проверяет числа словами. Цитата также не доказывает,
что предложение действительно было принято. Корректность фактов, отрицаний,
полнота, статус решений и смысловые сроки требуют проверки настоящей модели.
Такая точность не заявляется на основании тестовых doubles.

## Настройки и ошибки

Общие модель, timeout, `num_ctx` и `num_predict` — те же `HACKALEM_OLLAMA_*` и
`HACKALEM_LLM_*`, что у извлечения. Дополнительно:

| ENV | Default | Назначение |
| --- | --- | --- |
| `HACKALEM_SUMMARY_MAX_CHARS` | 60000 | Лимит символов исходного текста |
| `HACKALEM_SUMMARY_ATTEMPTS` | 2 | Всего попыток при невалидном ответе, 1–3 |

Превышение лимита текста или контекста дает 413, текст не обрезается. Обработка
длинных встреч по частям пока не реализована. Пустой транскрипт с пустым списком
поручений возвращает пустые разделы без обращения к LLM.

Ошибки: 409 — не готовы источники, разные версии, занято/готово; 503 — отсутствует
prompt или локальная модель/сервер; 504 — timeout; 502 `summary_invalid_output` —
ответ не прошел схему/проверки; 500 `summary_unavailable` — поврежденная запись SQLite.
Тексты встреч и внутренние ответы сервера в ошибки не включаются.

## Результаты проверки

Этап 8: 34 проверки prompt/извлечения/API прошли перед переходом к summary.
Итог этапа 9: **155 тестов прошли**, включая все предыдущие слои, `/health` — 200,
compileall без ошибок. Осталось прежнее предупреждение стороннего TestClient.
Проверены UTF-8, независимость от CWD, ошибки ресурсов, числовые изменения, ссылки,
условия, RU/KZ Unicode, сохранность нескольких сроков, перезапуск, конкурентные
запросы, несовпадение версий источников и повтор после невалидного ответа.

Ollama на localhost по-прежнему недоступна. Реальное формирование summary и его
качество не проверены. После установки модели прогоните оба примерных совещания
из источника (только реплики, без готового саммари) и вручную проверьте:
71%/94%/12% и единицы; отсутствие пострадавших; условность расторжения;
непринятые предложения; финальные три недели; смету за неделю и очередь за месяц;
отсутствие придуманного срока у подготовки шаблона договора. Отдельно нужна
оценка казахского и смешанного текста.
