# Этапы 15–16: протоколы, быстрые тесты и расход

## Источники и fixtures

`tests/fixtures/meeting_protocols.json` содержит **32 реплики первого протокола**
и **28 реплик второго** из приложений Б и В `ai-review/requirements.md`.
Сохранены порядок, имена говорящих и текст. Заголовки разделов, подписи должностей,
готовые саммари и таблицы результатов исключены из входных `segments`.
Тест сверяет каждую реплику с источником и проверяет полноту/порядок.

Поле `mock_response` — вручную подготовленный ответ для mocked LocalLLMClient,
а не результат настоящей модели. В запрос передаются только `segments`.
Ответы и готовые таблицы источника не подмешиваются в prompt.
Для протокола 1 fixture содержит десять безусловных и одно условное поручение из
реплик; для протокола 2 — шесть задач с milestones для переаттестации. Это вариант
группировки для тестов, а не требование ровно такого числа строк в продукте.
Пустые разделы summary в fixture не являются эталоном полноты саммари.

## Проверяемые случаи

| Правило | Исходный пример | Проверка |
| --- | --- | --- |
| Ответственный отличается от говорящего | Протокол 2, реплика 4: Данияр назначает Ерлана | Ответственный остаётся Ерланом, итоговый пересказ не меняет его на Ботагоз |
| Ответственный не выступал | Протокол 2: Ерлан отсутствует среди speaker | Поручение сохраняется |
| Ответственное подразделение | Протокол 1, реплика 6 | Юридический департамент не заменяется говорящим |
| Изменение срока | Протокол 1, реплики 17–20 и 31 | Итоговый срок к пятнадцатому октября; переговоры сохраняются в sources |
| Нет срока | Протокол 2, реплики 25–27 | У Салтанат `null`; пять рабочих дней остаются условием договора |
| Относительный срок | Протокол 2, реплики 4, 12, 18–19 | Недели, срок после совещания и milestones сохраняются без выдуманных дат |
| Нет дублей | Протокол 1, инструктаж и повтор в реплике 31 | Точный дубль объединяется, цитаты и ссылки сохраняются в задачах и summary |
| Условное решение | Протокол 1, реплика 13 | Расторжение договора остаётся conditional и в поручении, и в summary |
| Предложение не равно поручению | Протокол 1, реплика 21 отдельно; затем 21–23 с принятием | Mock без принятия не создаёт задачу; отдельный ответ с принятием сохраняет задачу |

Также проверены отклонение выдуманных исполнителя/даты/ID и конфликтующих старого
и нового сроков без автоматического дополнительного inference.

**Граница доказательства:** mock-тесты проверяют схемы, grounding, объединение
точных дублей и сохранение корректного ответа через сервисы. Они не доказывают,
что настоящая модель верно поняла ответственного, пересмотр срока или предложение.
Лексическая проверка не обнаружит все семантические ошибки: например, имя
председателя присутствует в источнике и само по себе не считается выдуманным.
Смысловые дубли с разными формулировками также требуют правильного ответа LLM.

## Быстрые тесты и ручная оценка

```powershell
.venv/Scripts/python.exe -m pytest tests/unit/test_protocol_analysis.py -q
.venv/Scripts/python.exe -m pytest tests/unit/test_analysis_metrics.py -q
.venv/Scripts/python.exe -m pytest -q
```

В новых protocol unit tests сетевые подключения запрещены через monkeypatch.
Настоящая LLM не вызывается. Результат этапа: **205 passed, 2 skipped** за 14,80 с.
Два пропуска — опциональные Chrome-тесты предыдущего этапа, включаемые отдельно
по [UI.md](UI.md). Сами 17 protocol-тестов прошли за 0,42 с в этой среде.
Осталось прежнее предупреждение Starlette TestClient, падений нет.

Отдельный manual-скрипт использует настоящий `LocalMeetingAnalyzer` и Ollama
на localhost. Без флага `--run-local` inference не выполняется:

```powershell
.venv/Scripts/python.exe scripts/evaluate_protocols.py
# Только после подготовки локальной модели и Ollama с OLLAMA_NO_CLOUD=1:
.venv/Scripts/python.exe scripts/evaluate_protocols.py --run-local
# При необходимости — только один протокол:
.venv/Scripts/python.exe scripts/evaluate_protocols.py --run-local --protocol 2
# Дополнительный независимый вход: предложение до его принятия:
.venv/Scripts/python.exe scripts/evaluate_protocols.py --run-local --include-proposal-window
```

По умолчанию manual-прогон анализирует два полных текстовых протокола: целевой
расход — по одному вызову на каждый, если они помещаются в контекст. Дополнительное
окно предложения — отдельный тестовый вход и дополнительный вызов, только по флагу.
Отчёт остаётся в `data/protocol-evaluation/report.json` вне Git. Скрипт не вызывает
LLM для оценки LLM: результаты, ручной reference и checklist проверяет человек.
Статус успешной генерации — `needs_human_review`, а не семантический `passed`.
При ошибке следующие кейсы не запускаются, `not_run` отражает пропуски.
В рамках этого этапа проверен безопасный запуск без флага; настоящий inference
не выполнялся и качество модели не объявляется подтверждённым.

## Метрики

`app/services/analysis_metrics.py` пишет одну JSON-запись `analysis_metrics` на
уровне INFO в стандартный лог приложения. Нет внешнего сборщика, платных API,
новых модельных запросов, скачивания tokenizer или отдельной БД для метрик.
Основные точки: `/analyze`, совместимый `/process`, GET `/result` и самостоятельный
вызов `LocalMeetingAnalyzer.analyze()` (включая manual-скрипт).
Старые отдельные диагностические extraction/summary endpoints этим счётчиком
совместного анализа не охвачены.

| Поле | Значение |
| --- | --- |
| `operation` | `analyze` или `result_read` |
| `meeting_id` | UUID встречи в API; `null` при прямом вызове сервиса |
| `transcript_characters` | Сумма `len(text)` исходных сегментов, поданных анализатору; не удваивается из-за chunks |
| `input_tokens_estimate` | Сумма приблизительных токенов входа **текущей операции**; 0 при чтении кеша |
| `input_tokens_estimate_method` | `utf8_bytes_div_4`: UTF-8 байты / 4 с округлением вверх |
| `input_tokens_estimate_scope` | System prompt + user JSON + JSON Schema, без server chat template |
| `model` | Модель анализа; при чтении — сохранённая исходная модель, даже если ENV изменён |
| `duration_seconds` | Монотонное время текущей операции в секундах |
| `cache_status` | `miss` для нового/отсутствующего анализа, `hit` для сохранённого результата |
| `llm_calls` | Число попыток `LocalLLMClient.generate_json()` в текущей операции |
| `status` | `success` или `error` |

Оценка токенов — грубый показатель, особенно для RU/KZ, а не фактическое число
токенов модели и не стоимость в деньгах. Она не используется для решения о chunking.
При chunking суммируются входы всех попыток, включая отклонённый полный вход и
финальный merge. Метаданные Ollama `/api/show` не считаются генерацией.
`llm_calls` считает обращения к интерфейсу, включая ошибку настройки/сети до
фактического inference. Число успешных ответов отдельно остаётся в
`completed_generations` сохранённого анализа.

Для API `duration_seconds` охватывает pipeline целиком, включая STT/диаризацию и
экспорт; при прямом вызове — анализ и валидацию; для GET — чтение/сборку ответа
до HTTP-сериализации. Ошибка тоже логируется. Если pipeline не дошёл до источников,
`transcript_characters=null`; это отличается от пустого транскрипта с 0 символов.
Исключения, prompts, ответы, цитаты, названия встреч и сам текст в метрики не входят.

`ContextVar` изолирует одновременные операции. Анализатор внутри pipeline использует
его счётчик и не пишет второй дублирующий event. При ошибке контекст освобождается.
Имя модели добавлено к сохраняемому `MeetingAnalysis` как необязательное поле;
старые JSON остаются читаемыми. Для них имя берётся из сохранённого extraction,
если доступно; текущая ENV-модель не выдаётся за историческую.

## Проверенный расход

| Сценарий | cache | LLM calls текущего запроса |
| --- | --- | --- |
| Обычное совещание, первый совместный анализ | miss | **1** |
| Повторное открытие GET `/result`, в том числе после перезапуска | hit | **0** |
| Повтор POST уже готового pipeline | hit | **0** |
| Повтор после ошибки экспорта | hit | **0** |
| Чтение пока неготового результата (409) | miss | **0** |
| Пустой вход прямому анализатору | miss | **0** |
| Overflow, два chunks, один merge в тесте | miss | **4 попытки**, из них 3 завершены |

Эти значения подтверждены тестами с учётом реальных обращений к mocked client,
а не просто записаны константами в лог. API-проверки также подтверждают сохранение
имени исходной модели после изменения ENV и отсутствие повторного STT/диаризации.
