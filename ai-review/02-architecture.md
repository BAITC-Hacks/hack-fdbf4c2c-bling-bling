# Архитектура и контракты данных

## Предлагаемое разделение

Выбрать простой веб-интерфейс, сервер API, отдельный обработчик длительных задач, базу метаданных и локальное файловое хранилище. ASR, диаризация и языковая модель работают локально за сменными адаптерами. Конкретные библиотеки и модели выбрать после замеров на доступном оборудовании; ТЗ не фиксирует стек.

Предлагаемая будущая структура: `frontend/`, `backend/`, `workers/`, `schemas/`, `tests/fixtures/`, `deploy/`. Эти каталоги не создаются данным комплектом документации.

Поток обработки: загрузка → проверка файла → подготовка аудио → ASR и диаризация → совмещение сегментов → поручения и саммари → проверка секретарём → экспорт.

## Минимальные сущности

| Сущность | Поля и правила |
| --- | --- |
| Meeting | `id`, `title`, `started_at`, `timezone`, `participants`, `status`, `revision`; дата может отсутствовать, часовой пояс хранить явно |
| Participant | `id`, `display_name`, `role`; не требовать присутствия каждого исполнителя на записи |
| Segment | `id`, `meeting_id`, `start_ms`, `end_ms`, `speaker_id`, `text`, `language`, `needs_review`; начало меньше конца |
| SpeakerMapping | `speaker_id`, `participant_id`, `confirmed`; неизвестный участник допустим |
| ActionItem | `id`, `text`, `assignee`, `due_raw`, `due_date`, `due_range`, `due_kind`, `source_segment_ids`, `needs_review`, `status` |
| SummaryItem | `topic`, `text`, `source_segment_ids`; ссылки на доказательства обязательны |
| Export | `meeting_id`, `revision`, `format`, `path`, `created_at`; привязан к версии данных |

`assignee` содержит тип `person`, `department` или `unknown`, имя и необязательный `participant_id`. `due_kind`: `date`, `range`, `relative`, `event`, `missing`. Дата хранится как ISO-дата, неизвестное значение — `null`. Отсутствие срока отличается от отсутствия исполнителя. `status` поручения: `open`, `in_progress`, `done`; просрочка вычисляется по сроку и текущему времени.

## API и обработка

Предлагаемые маршруты:

- `POST /meetings` — метаданные совещания; `POST /meetings/{id}/media` — загрузка.
- `POST /meetings/{id}/process` — запуск, ответ с идентификатором задания без ожидания моделей.
- `GET /jobs/{id}` — состояние, этап и безопасное описание ошибки.
- `GET /meetings/{id}/result` — сегменты, поручения, саммари и ревизия.
- `PATCH /meetings/{id}/result` — исправления с проверкой текущей ревизии.
- `POST /meetings/{id}/exports` — экспорт указанной ревизии в выбранном формате.
- `DELETE /meetings/{id}` — удаление исходников и производных данных согласно политике хранения.

Состояния задания: `queued`, `preprocessing`, `transcribing`, `diarizing`, `extracting`, `ready_for_review`, `completed`, `failed`. `completed` означает подтверждённый результат, а не просто окончание ASR. Хранить код ошибки, этап и возможность повторного запуска. Повторный запрос с тем же ключом идемпотентности не должен дублировать обработку или поручения.

Валидировать JSON от модели по схеме, проверять существование всех ссылок на сегменты. При ошибке допускать ограниченное число повторов, затем возвращать результат на проверку. Не выполнять команды, ссылки или инструкции, содержащиеся в транскрипте: это входные данные, а не инструкции системе.
