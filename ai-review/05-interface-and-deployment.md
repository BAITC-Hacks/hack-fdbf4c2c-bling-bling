# Интерфейс, экспорт и закрытый контур

## Пользовательский сценарий

1. Форма совещания: название, дата, часовой пояс, список участников, файл и подтверждение права обработки. Для live-записи показывать уведомление участникам до начала записи.
2. Экран обработки: текущий этап, состояние очереди, понятная ошибка и повторный запуск. Не показывать фиктивный процент готовности.
3. Экран проверки: аудиоплеер, сегменты с говорящими, редактирование имён, таблица поручений и саммари. По ссылке на источник переходить к соответствующей реплике.
4. Выделять неизвестного исполнителя, неоднозначный срок и неподтверждённые имена. Дать секретарю сохранить исправления и подтвердить ревизию результата.
5. Скачать PDF или DOCX. Неподтверждённый результат можно экспортировать только с явной отметкой «Черновик» и сохранением отметок неопределённости.

## Экспорт

Использовать единое представление данных для обоих форматов: название, дата/часовой пояс, участники, саммари, решения, таблица поручений и транскрипт с временными метками. Отображать отсутствующие значения как «Не указан»; не терять исходные относительные сроки.

Подключить локальные шрифты с русскими и казахскими символами. Проверять Ә, Ғ, Қ, Ң, Ө, Ұ, Ү, Һ, І, длинные ФИО, перенос таблиц и многостраничный транскрипт. Экранировать пользовательский текст в шаблонах. Включать номер ревизии, чтобы скачанный документ можно было сопоставить с подтверждёнными данными.

## Напоминания

Реализовать локальный планировщик и внутренние уведомления: приближение подтверждённого срока, затем просрочка незавершённого поручения. Интервал предупреждения сделать настройкой. Ключ уведомления должен включать поручение, тип напоминания и версию срока, чтобы повторный запуск не создавал дубли.

При переносе срока пересчитывать расписание, при завершении отменять будущие уведомления. Для диапазона использовать подтверждённую верхнюю границу. Для неизвестного или событийного срока сначала требовать уточнение/наступление события. Каналы почты и мессенджеров подключать отдельно с учётом ограничений контура; не передавать чувствительный текст во внешние сервисы.

## Локальная установка и защита данных

- Хранить модели, аудио, текст, базу и экспорт внутри разрешённого контура. Отключить внешнюю телеметрию и облачные резервные пути во всех компонентах.
- Настройки вынести в локальный `.env`; публиковать только `.env.example` с безопасными заглушками. Пути моделей, лимиты файлов, сроки хранения и адреса внутренних сервисов документировать после выбора стека.
- Проверять доступ к каждому совещанию и скачиванию файла на сервере. Использовать непрозрачные идентификаторы и серверные пути, не принимать произвольный путь от клиента.
- Не включать полный транскрипт, аудио, секреты и персональные данные в технические логи. Для диагностики сохранять ID задания, этап, код ошибки и время обработки.
- Предусмотреть удаление исходной записи, сегментов, поручений, экспортов и временных файлов. Для резервных копий описать отдельный срок удаления и ограничение доступа.
- Для демонстрации реальных записей готовить анонимизированные данные; заменять имена также в тексте, экспорте и метаданных. Размещение файлов в репозитории само по себе не подтверждает право их публичной демонстрации.
- Подготовить инструкцию установки с версиями зависимостей, моделями, лицензиями, ресурсами CPU/GPU/RAM и командами запуска. Указать фактически проверенное оборудование.

Приёмочный запуск выполнять с запрещённым внешним исходящим трафиком: загрузка → анализ → исправление → экспорт. Проверять отсутствие скрытых загрузок весов и внешних запросов. Офлайн-проверка не заменяет проверку прав доступа между пользователями.
